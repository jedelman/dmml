# 2026-09-19 — The index

Jason: *"Is there an rdf in memory db for Haskell?"* → *"Definitely write the index!"*

## The question behind the question

Pruning removed the simulations. It did not remove the **pairs**. `group_into_generations`
still asked `may_conflict` about every one of them, which is quadratic in candidates however
cheap each answer is — and at 23 candidates a cheap quadratic is invisible, which is exactly
how a quadratic gets left in.

The survey of the Haskell RDF ecosystem is in the conversation log; the short version is that
`rdf4h` is maintained and gives you three in-memory graph implementations, `swish` gives you
inference, and **nobody has written a SPARQL engine in Haskell** — `hsparql` generates queries
and ships them to a remote endpoint. But the more useful finding was that a triple store is
the wrong shape for DMML facts, which carry commits, `consumes` provenance, value types and
guard structure. `written-world` got into RDF by *reifying*, which is where the query
performance you came for goes to die.

What was actually wanted was the one thing a store would have given for free: **a pattern
index**.

## Invert the question

Instead of asking each B in turn whether it reads what A touches, ask the slots A touches
**who reads them**. Three buckets, mirroring the three cases `may_conflict` handles:

- `exact` — a guard on a named subject, keyed `(subject, predicate)`.
- `any_subject` — a guard over a `?binder` or `$param`, which matches whatever subject a
  write happens to carry, so keyed by predicate alone.
- `everything` — a candidate whose guard the reader could not parse. It conflicts with every
  write, so it is carried into every answer.

Cost goes from O(candidates²) intersections to O(candidates × touches) lookups plus the
conflicts actually found. Thirty lines.

## Agreement first, speed second

`may_conflict` stays, and is now explicitly **the specification**. A pair the index wrongly
calls independent is two firings applied in the same round that can invalidate each other — a
corrupted world, silently, with nothing else in the toolchain able to see it. So the index is
checked against its specification two ways:

- **`DMML_INDEX_SELFCHECK=1`** in the driver recomputes each round's partner list the slow way
  and asserts the *ordered lists* are equal. Run over all four demo scenarios: **39 grouping
  rounds, no disagreement.**
- **`index-scaling-bench.py`**, now in CI, does the same at sizes no real run has produced
  yet. It needs no Haskell binary — it imports `driver.py` and compares the two answers
  directly.

And the four dry-run transcripts are **byte-identical** to the pre-index driver, including the
`grouping:` lines, so the pruned counts match too.

## What it costs

Synthetic, but calibrated rather than invented: touch/read set sizes and the wildcard fraction
are sampled from the largest round of a real `cannon-fanout` run (31 candidates; 1–4 reads and
1–3 touches each; 2 wildcard reads of 96; no unparsed guards).

```
 candidates       pairs  conflicts    pairwise     indexed   speedup
         50        1225          0      0.001s      0.000s      9.3x
        200       19900         21      0.012s      0.000s     37.7x
        800      319600        165      0.191s      0.001s    135.4x
       3200     5118400       4542      3.200s      0.019s    169.0x
      12800    81913600      71075     58.589s      0.110s    532.0x
```

**On the four demos: no wall-clock change at all** (7.3s/37.9s/11.9s/3.9s, within noise of the
pairwise driver). That is the honest headline. The pair loop was never the cost at 23
candidates — this is a fix for the size the cannon is heading toward, bought now because the
measurement that would justify it later is cheaper to take today.

## What it does not fix

The index helps when candidates are mostly strangers. A round where most of them really do
collide degrades to the pairwise cost it started from — and correctly so, because those pairs
have to be probed. What remains after that is the probe batch itself, which is real work.

## Still open

- The guard reader is still a regex over machine text — a second parser for a language that
  already has one. Conservative when it fails, so never wrong in the dangerous direction, but
  `scan-candidates` should report a transition's read set directly.
- No driver dry-run is wired into CI, so `DMML_INDEX_SELFCHECK` only runs by hand.
- `render-prose` and `list-candidates` are still one subprocess per round each.
